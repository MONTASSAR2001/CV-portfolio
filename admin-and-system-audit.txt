1.2  AUTHENTICATION FLOW ANALYSIS
──────────────────────────────────
  Files: login.tsx, routes/index.tsx (AdminDashboard)

  WHAT IS WORKING:
  ✅ login.tsx calls supabase.auth.signInWithPassword() — real Supabase auth.
  ✅ On success, navigates to "/" (dashboard).
  ✅ AdminDashboard (index.tsx) runs a session check on mount via
     supabase.auth.getSession(). If no session → redirects to /login.
  ✅ An onAuthStateChange listener watches for token expiry or logout from
     another tab — correctly handles session invalidation reactively.
  ✅ "Block render until session confirmed" pattern prevents admin UI flash.
  ✅ Logout button calls supabase.auth.signOut() and redirects to /login.

  🔴 CRITICAL SECURITY GAP — NO ADMIN ROLE CHECK:
  The auth flow only verifies that *a* Supabase session exists. It does NOT
  verify that the authenticated user has an 'admin' role or belongs to an
  admin group. This means:

    - ANY user who has a valid Nexus account (free tier, regular signup) could
      theoretically access the admin panel at the admin app's URL if they know it.
    - There is no call to supabase.from("profiles").select("role") or
      check of user.app_metadata.role or custom claims.

  REQUIRED FIX:
  In AdminDashboard's useEffect, after confirming a session exists, add:

    const { data: profile } = await supabase
      .from("profiles")
      .select("role")
      .eq("id", session.user.id)
      .single();

    if (profile?.role !== "admin") {
      await supabase.auth.signOut();
      navigate({ to: "/login" });
      return; // show "Access denied" error on login page
    }

  Alternatively, use Supabase custom JWT claims (app_metadata.role = "admin")
  set server-side, and check user.app_metadata.role in the client.

  🔴 SECONDARY GAP — login.tsx has no role check either:
  After signInWithPassword() succeeds, login.tsx immediately navigates to "/".
  It should perform the same role check before redirecting.

  🟡 COSMETIC ISSUE: The sidebar user widget (bottom-left) shows a hardcoded
  avatar name "Daniel Rhodes" and email "daniel@infinitybugs.io". This should
  be populated from supabase.auth.getUser() dynamically.

───────────────────────────────────────────────────────
  File: src/lib/server-fns.ts (lines 273-368)

  SECURITY:
  ✅ validateSessionToken() called FIRST, before any Groq API call.
     It creates a server-side Supabase client and calls getUser(accessToken),
     which validates the JWT against Supabase auth servers. Invalid tokens
     throw "Unauthorized" and abort the request. ✓

  ✅ Input validated with Zod before handler runs:
     - cvText: min 80 chars, max 12,000 chars (prevents prompt injection via
       extremely large payloads)
     - accessToken: min 1 char (required)

  ✅ GROQ_API_KEY is server-only (no VITE_ prefix) — never shipped to client
     bundle. ✓

  ✅ AI response uses response_format: { type: "json_object" } which forces
     Groq to return valid JSON, reducing hallucination risk. ✓

  ✅ Structural validation of AI response before returning to client:
     Checks personalInfo, experience (Array), skills (Array). ✓

  ✅ Temperature 0.3 — correct for deterministic extraction (not creative
     generation). ✓

  PDF PIPELINE:
  ✅ pdf-extractor.ts uses pdfjs-dist with proper worker setup via Vite's
     import.meta.url pattern. ✓
  ✅ Page-by-page text extraction with page.cleanup() after each page to
     prevent memory leaks. ✓
  ✅ Minimum 80-char guard in AIImportModal before calling the server function,
     protecting against scanned/image-only PDFs. ✓
  ✅ Text is sliced to 12,000 chars before the API call, staying within
     Groq's context window safely. ✓

  🟡 MINOR ISSUE — No rate limiting:
     The server function has no per-user rate limiting. A user could spam the
     endpoint repeatedly. Recommended: add a simple token-bucket check against
     a "api_usage" table in Supabase, or use Groq's built-in rate limits as
     the backstop (acceptable for MVP).

  🟡 MINOR ISSUE — No education null-guard:
     The structural validation checks personalInfo, experience, and skills,
     but NOT education. If Groq returns { education: null } instead of [],
     the client may crash when trying to map over it.
     Recommended: add `&& Array.isArray(parsed.education)` to the check.

  STATUS: parseResumeWithAI is SECURE and functionally correct for production.
  Two minor improvements recommended but not blocking.

3.1  REQUIRED SUPABASE TABLES (CLIENT APP)
────────────────────────────────────────────

  TABLE: cvs
  ───────────
  Purpose: Store saved CV data from CV Studio
  Referenced by: cv-studio.tsx (save), dashboard.tsx (count)
  Schema:
    id          UUID DEFAULT gen_random_uuid() PRIMARY KEY
    user_id     UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE
    cv_data_json JSONB NOT NULL   -- full CvState object
    updated_at  TIMESTAMPTZ DEFAULT now()
    created_at  TIMESTAMPTZ DEFAULT now()
  Constraint: UNIQUE(user_id)  -- one CV per user (upsert on conflict)

  RLS Policies required:
    ENABLE ROW LEVEL SECURITY on cvs;
    CREATE POLICY "Users can read own CV"
      ON cvs FOR SELECT USING (auth.uid() = user_id);
    CREATE POLICY "Users can upsert own CV"
      ON cvs FOR INSERT WITH CHECK (auth.uid() = user_id);
    CREATE POLICY "Users can update own CV"
      ON cvs FOR UPDATE USING (auth.uid() = user_id);


  TABLE: portfolios
  ──────────────────
  Purpose: Store deployed portfolio records from Portfolio Builder
  Referenced by: portfolio-builder.tsx (insert), dashboard.tsx (select)
  Schema:
    id           UUID DEFAULT gen_random_uuid() PRIMARY KEY
    user_id      UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE
    template_id  TEXT NOT NULL        -- e.g. "vogue", "architect"
    content_json JSONB NOT NULL       -- PortfolioContent object
    deployed_url TEXT NOT NULL        -- full Vercel URL
    created_at   TIMESTAMPTZ DEFAULT now()

  RLS Policies required:
    ENABLE ROW LEVEL SECURITY on portfolios;
    CREATE POLICY "Users can read own portfolios"
      ON portfolios FOR SELECT USING (auth.uid() = user_id);
    CREATE POLICY "Users can insert own portfolios"
      ON portfolios FOR INSERT WITH CHECK (auth.uid() = user_id);
    -- No UPDATE/DELETE needed for MVP (immutable deployment records)


3.2  REQUIRED SUPABASE TABLES (SHARED / ADMIN)
────────────────────────────────────────────────

  TABLE: profiles
  ────────────────
  Purpose: Extended user metadata (role, plan, token balance, status)
  Referenced by: Admin Users & Billing view, future client subscription gating
  Schema:
    id            UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE
    email         TEXT                    -- denormalised for admin queries
    role          TEXT DEFAULT 'user'     -- 'user' | 'admin'
    plan_type     TEXT DEFAULT 'free'     -- 'free' | 'pro' | 'enterprise'
    token_balance INTEGER DEFAULT 0
    status        TEXT DEFAULT 'active'   -- 'active' | 'suspended' | 'flagged'
    created_at    TIMESTAMPTZ DEFAULT now()
    updated_at    TIMESTAMPTZ DEFAULT now()

  RLS Policies required:
    ENABLE ROW LEVEL SECURITY on profiles;
    CREATE POLICY "Users can read own profile"
      ON profiles FOR SELECT USING (auth.uid() = id);
    CREATE POLICY "Users can update own profile (limited fields)"
      ON profiles FOR UPDATE USING (auth.uid() = id)
      WITH CHECK (role = 'user');  -- prevent self-promotion to admin
    CREATE POLICY "Admins can read all profiles"
      ON profiles FOR SELECT USING (
        EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'admin')
      );
    CREATE POLICY "Admins can update all profiles"
      ON profiles FOR UPDATE USING (
        EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'admin')
      );

  Trigger: Auto-create profile row on new user signup:
    CREATE OR REPLACE FUNCTION public.handle_new_user()
    RETURNS TRIGGER AS $$
    BEGIN
      INSERT INTO public.profiles (id, email)
      VALUES (NEW.id, NEW.email);
      RETURN NEW;
    END;
    $$ LANGUAGE plpgsql SECURITY DEFINER;

    CREATE TRIGGER on_auth_user_created
      AFTER INSERT ON auth.users
      FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();

3.4  EDGE FUNCTIONS REQUIRED (SERVICE ROLE OPERATIONS)
────────────────────────────────────────────────────────
  The following operations require the Supabase service_role key and CANNOT
  be done client-side safely. They must be implemented as Supabase Edge
  Functions (Deno) deployed to the Supabase project:

  1. list-users
     Calls supabase.auth.admin.listUsers() to return all auth.users
     for the Admin Users & Billing view.
     Auth guard: verify caller has role='admin' in profiles.

  2. delete-user
     Calls supabase.auth.admin.deleteUser(userId) for account deletion.
     Used by both the "Delete account" button in settings.tsx (user self-
     deletion) and the "Ban" button in the admin Users view.
     Auth guard for admin use: verify caller has role='admin'.
     Auth guard for self-deletion: verify userId = caller's own ID.

  3. update-user-role  (admin only)
     Updates profiles.role for a given user.
     Auth guard: verify caller has role='admin'.
